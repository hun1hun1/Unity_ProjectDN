# 카드 강화 구현 설계

2026-10-19에 초안을 작성했고 2026-11-08에 구현 상태를 갱신했습니다.

휴식 패널에는 `카드 강화` 버튼이 `준비 중`으로 표시되어 있습니다. `CardData.upgradedCard`, 강화 대상 선택·비교 화면, 덱 교체 API는 앞으로 구현할 범위입니다. 아래 코드는 그 구조의 예시입니다.

관련 문서: [맵과 런 진행·콘텐츠 노드 확장](MapSystem.md), [카드 설명](CardDescriptions.md), [전투 보상](BattleRewards.md).

## 현재 구조

| 구성 | 현재 역할 | 소스 |
|---|---|---|
| `CardData` | 이름·코스트·종류·희귀도·효과 목록·카드 특성 등을 가진 ScriptableObject | [CardData.cs](../Assets/Scripts/Card/CardData.cs) |
| `CardEffect` | 피해·방어·상태이상·지연 등의 실행과 미리보기를 정의하는 ScriptableObject | [CardEffect.cs](../Assets/Scripts/Card/CardEffects/CardEffect.cs) |
| `RunDeckState` | 꿈·악몽 각각의 `List<CardData>`와 읽기 전용 뷰 | [RunDeckInventory.cs](../Assets/Scripts/BattleCharacter/Player/RunDeckInventory.cs) |
| `RunDeckInventory` | 시작 덱 DB 쌍별 런 덱을 보관하고 새 런에서 초기화 | 같은 파일 |
| `DeckController` | 런 덱에 접근하고 전투용 드로우·버림·소멸 더미 관리 | [DeckController.cs](../Assets/Scripts/BattleCharacter/Player/DeckController.cs) |
| `DeckCardUI` | 전달받은 카드 정의 표시 | [DeckCardUI.cs](../Assets/Scripts/UI/DeckCardUI.cs) |
| `DeckListUI` | 덱 목록 표시. 현재는 전달받은 목록의 복사본을 섞어서 표시 | [DeckListUI.cs](../Assets/Scripts/UI/DeckListUI.cs) |

런 덱은 시작 데이터베이스의 목록을 복사하지만, 각 원소의 `CardData`와 그 안의 `CardEffect`는 공유 에셋 참조입니다. 같은 카드 에셋을 여러 덱 항목이 참조할 수 있습니다. 현재 구조에는 보유 카드 한 장마다 고유 ID나 강화 레벨을 가진 별도의 카드 인스턴스가 없습니다.

## 기본 방식: 강화 카드 정의로 한 항목 교체

기존 `CardData → CardEffect` 조합을 유지합니다. 원본 카드와 강화 카드를 별도 에셋으로 만들고, 확인 시 선택한 런 덱 항목 하나만 강화 카드 참조로 교체합니다.

```text
런 덱: [공격, 공격, 방어]
              ↑ 두 번째 항목 선택
런 덱: [공격, 공격+, 방어]
```

원본 카드 에셋이나 시작 덱 데이터베이스를 수정하지 않으며, 다음 새 런은 기존 시작 덱으로 시작합니다.

### 추가할 카드 필드 예시

```csharp
// CardData에 추가할 예정인 필드. 현재 구현에는 없습니다.
public CardData upgradedCard;
```

- 원본 카드의 `upgradedCard`에 강화 결과 에셋을 연결합니다.
- 강화 경로의 마지막 카드에는 연결하지 않습니다. 그 카드는 강화 대상에서 제외합니다.
- 한 번만 강화한다면 `공격 → 공격+ → null`로 구성할 수 있습니다.
- 여러 단계 강화가 필요하면 연결을 늘릴 수 있지만, 허용 횟수와 밸런스는 별도로 결정해야 합니다.
- 자기 자신을 가리키거나 순환하는 연결, 꿈·악몽 덱 종류가 달라지는 연결은 검증에서 거부합니다.

## 효과 에셋 구성

아래 수치는 설명용 예시이며 실제 밸런스를 확정하지 않습니다.

| 항목 | 원본 카드 | 강화 카드 |
|---|---|---|
| 이름 | 공격 | 공격+ |
| 카드 에셋 | 원본 `CardData` | 별도의 강화 `CardData` |
| 피해 효과 | 원본 `DamageEffect`, 피해 6 | 별도의 강화 `DamageEffect`, 피해 9 |
| 바뀌지 않는 효과 | 기존 효과 참조 | 같은 효과 참조 재사용 가능 |

**값이 달라지는 효과는 별도 에셋을 만듭니다.** 원본 `DamageEffect.damage`를 직접 변경하면 그 효과를 참조하는 다른 카드에도 영향을 줍니다. `CardData`만 복제하고 참조된 효과의 값을 수정해도 효과 공유 문제는 남습니다.

피해뿐 아니라 코스트, 방어도, 필수 탄약, 지속 기간, 지연 턴 수, 효과 추가·제거 등을 강화 카드에서 정의할 수 있습니다. 지연·조건부 효과의 내부 값이 바뀐다면 필요한 상위·하위 효과 에셋도 분리하고, 변경하지 않는 정의만 공유합니다.

강화와 관계없는 `costMode`, `deckType`, `type`, `rarity`, `exhaustOnUse`, 지속 카드 설정과 `turnStartEffects` 등이 의도치 않게 달라지지 않도록 비교합니다. 강화 카드가 일반 보상 풀에 자동으로 포함되는 것은 아니며, 기존 보상 DB는 별도 요구가 없다면 유지합니다.

## 선택한 한 장을 정확히 식별하는 방법

현재 자료구조를 유지한다면 강화 UI에 표시할 항목마다 다음 정보를 함께 보관합니다.

- 선택 시점의 런과 대상 런 덱 식별 정보
- 꿈 또는 악몽 덱 종류
- 화면의 정렬 순서와 별개인 실제 런 덱 인덱스
- 선택 당시의 원본 `CardData`
- 선택 후 덱이 변경되었는지 판별할 정보

`CardData` 참조만으로는 같은 카드를 여러 장 가진 경우 어느 한 장을 선택했는지 구분할 수 없습니다. 화면에서 두 번째로 보인 카드가 실제 런 덱의 두 번째 항목이라고 가정해서도 안 됩니다. 특히 현재 `DeckListUI.ShowCards()`는 표시 목록을 섞으므로, 시각 요소를 재사용하더라도 원본 항목의 인덱스 매핑을 추가해야 합니다.

확인 전후로 덱이 바뀔 수 있다면 인덱스와 예상 카드 참조만 비교해서는 부족합니다. 동일 카드가 여러 장일 때 삭제·삽입으로 위치가 바뀌어도 같은 참조가 남을 수 있기 때문입니다. 덱 변경 버전을 함께 검증하거나 선택 중 덱 변경을 막는 정책이 필요합니다. 기존 `RunDeckInventory.GameVersion`은 새 게임 구분용이므로 일반적인 덱 변경 버전처럼 사용하지 않습니다.

향후 카드 한 장마다 영구 수치나 서로 다른 부가 속성을 붙여야 한다면 고유 ID를 가진 런 카드 인스턴스 구조를 검토합니다. 고정된 강화 정의로 교체하는 현재 설계에 그 전환을 필수로 포함하지는 않습니다.

## 런 덱 강화 API — 추가 예정

맵 씬에서 사용할 런 덱 조회·교체 기능을 `RunDeckInventory` 또는 별도의 런 덱 서비스에 마련합니다. 현재 인벤토리는 시작 DB 쌍을 키로 사용하므로 어느 덱을 변경할지 명확히 식별해야 합니다. BattleScene의 `DeckController`를 맵 씬에 새로 생성해 접근하지 않습니다.

확정 처리는 다음 순서를 따릅니다.

1. 현재 런·층·노드와 강화 처리 가능 상태를 확인합니다.
2. 선택 당시의 덱과 인덱스가 유효하고, 이후 덱이 바뀌지 않았는지 확인합니다.
3. 해당 항목이 예상 원본 카드인지 확인합니다.
4. 유효한 강화 결과와 동일한 꿈·악몽 덱 종류인지 확인합니다.
5. 비용이 있다면 지불 가능 여부를 확인하고, 교체와 비용 지불이 함께 성공하도록 처리합니다. 실패 시 비용만 차감되면 안 됩니다.
6. 해당 항목 하나만 교체하고 변경을 알립니다. 같은 확인 입력이 다시 들어와도 두 번 처리되지 않게 합니다.

```csharp
// 위 검증을 통과한 뒤 실행하는 핵심 처리의 개념 예시입니다.
// deck, selectedIndex, selectedCard는 실제 구현에서 대상 런 덱과 선택 정보로 구합니다.
deck[selectedIndex] = selectedCard.upgradedCard;
```

현재 `RemoveCardFromDeck()`은 일치하는 첫 번째 항목을 제거하고, `AddCardToDeck()`은 전투 버림 더미에도 카드를 추가합니다. 따라서 이 두 메서드를 조합해 강화 대상 한 장을 교체하는 대신, 맵의 런 덱 항목 교체 API를 별도로 만듭니다.

## 강화 UI와 노드 연결 — 추가 예정

```text
휴식 노드 진입
  → 카드 강화 선택
  → 강화 가능한 런 덱 항목 표시
  → 한 장 선택
  → 원본과 강화 결과 비교
  → 확인 버튼
  → 검증 및 해당 항목 교체
  → 결과 표시·이용 종료
  → 저장 성공 시 휴식 노드 완료
```

- 선택과 미리보기만으로 카드를 교체하거나 비용을 소모하지 않습니다.
- 강화 가능한 카드가 없으면 안내와 이용 종료 경로가 있어야 합니다.
- 원본·강화 카드 모두 기존 `DeckCardUI.SetCard()`로 표시할 수 있습니다. 맵의 비교 설명은 기본 수치 기준으로 표시하도록 `applyStatusModifiers: false`를 사용합니다.
- 설명의 `{damage:0}`, `{block:0}` 같은 기존 토큰은 각 카드의 효과 목록을 기준으로 계산됩니다. 고정 숫자로 작성한 설명은 강화 카드에서도 직접 수정해야 합니다. 효과 목록 순서가 바뀌면 토큰 경로도 점검합니다.
- 선택 테두리와 확인 방식은 현재 카드 보상 UI와 같은 상호작용을 사용할 수 있지만, 보상용 `ConfirmCard()`는 카드를 새로 지급하는 동작이므로 강화 처리에 그대로 연결하지 않습니다.
- 휴식에 등록된 `RestHandler`에서 강화 선택 화면을 열도록 연결합니다. 카드 교체와 노드 완료의 저장 방식은 [노드 체크포인트](RunCheckpoints.md#비전투-노드-연결)의 방문 검증과 저장 계약을 따릅니다.
- 노드당 강화 가능 횟수, 가격, 취소·건너뛰기 가능 여부는 아직 미정입니다. 이용 종료 시점은 이 정책에 따라 정합니다.

## 다음 전투와 새 런

현재 `DeckController.ResetForBattle()`은 런 덱을 전투용 드로우 더미에 복사합니다. 맵에서 같은 런 덱을 교체하면 다음 BattleScene 진입 시 강화 정의가 복사되는 구조입니다. 손패·드로우·버림 더미를 직접 수정하는 기능은 이 맵 강화 설계에 포함하지 않습니다.

강화된 참조는 현재 런에서만 유지합니다. `RunDeckInventory.ResetForNewGame()` 이후에는 시작 DB에서 덱을 다시 구성하므로 강화 전 시작 덱으로 돌아갑니다. 현재 이어서 하기 저장은 보유 덱의 카드 참조를 에셋 ID로 기록합니다. 강화 결과를 실제로 저장하려면 결과 카드 에셋이 저장 카탈로그에 포함되어야 합니다.

## 구현 시 확인할 항목 — 예정

- 같은 원본 카드가 여러 장일 때 선택한 덱 항목 하나만 교체됩니다.
- 선택·미리보기·취소·오류 시 덱과 비용이 바뀌지 않습니다.
- 확인을 연속으로 눌러도 한 번만 적용됩니다.
- 선택 후 덱 변경이나 새 런 시작이 발생하면 오래된 선택은 거부됩니다.
- 강화 불가·자기 참조·순환 연결·덱 종류 불일치·범위 밖 인덱스를 거부합니다.
- 원본 `CardData`, 공유 효과, 시작 DB와 보상 DB가 바뀌지 않습니다.
- 강화 전후 설명과 코스트·탄약·지속·지연 설정이 의도대로 표시·실행됩니다.
- 맵을 떠나 다음 전투에서 강화 카드가 사용되고, 새 런에서는 시작 덱으로 복원됩니다.
- 강화할 카드가 없거나 비용이 부족해도 UI와 노드 진행이 멈추지 않습니다.

위 항목은 향후 구현의 검증 기준입니다. 이 문서 작성으로 강화 기능을 구현하거나 강화 테스트를 실행한 것은 아닙니다.
